ABSTRACT  
Infrastructure -As-Code (IaC) templates like Terraform, AWS CloudFormation, Kubernetes manifests and Helm 
charts play a role in developing multi -cloud environment solutions. Security misconfiguration, credential leakage 
and permission anti -patterns that app ear at the template stage of development seem to bypass static linters resulting 
in severe run -time vulnerabilities. Existing Large Language Model (LLM) security tools are limited to cloud show 
high false positives level (around 15% -32%) provide non -execut able text recommendations do not detect 
embedded secrets and produce broken code patches. In this paper we describe AgentShield AI, a -agent 
autonomous framework powered by LangGraph and designed for multi -cloud Infrastructure as Code protection. 
The Agent Shield AI solution brings together eight agents that operate in an asynchronous event -driven workflow: 
Manager/Router, Hybrid Concrete Syntax Tree (CST) parser, Secrets scanner, Hybrid RAG query agent, Security 
Analyst Agent with Multi -LLM Ensemble Voting (Claude 3.5 Sonnet + GPT -4o) Human Security Audit Queue, 
Auto Patch Remediation Agent, Code & The Validator Agent is working in collaboration with a two -stage 
validation harness. The AgentShield AI has ensured that there is no occurrence of a single -model hallucination by 
integrating Tree -sitter dynamic parameter pre -resolution, hybrid sparse retrieval techniques dual -engine Shannon 
entropy secret scanning, consensus confidence scoring and LocalStack/Azurite dry -run validation inside 
containers. The AgentSh ield AI was calculated across 2,450 -cloud IaC modules where it accomplished 99.1% 
detection accuracy 98.4% recall, false -positive percentages, below 0.05%, 97.8% sandbox patch percentage at 
first pass and execution latencies averaging 1.84 seconds for eve ry template.

1. Introduction  
As outlined in [1], infrastructure as code (IaC) has revolutionized the field of cloud architecture and 
engineering. Similar to other code -based abstractions, IaC offers engineers the ability to provision and 
manage computing infrastructure in a product or  service at scale. Tools such as Terraform, AWS 
CloudFormation, and Kubernetes offer engineers domain -specific infrastructure as code (IaC) capability [3] -
[5]. 
There are security concerns associated with the widespread adoption of IaC. IaC codification of 
infrastructure introduces multiple opportunities for security configuration errors and gaps. For example, IaC 
definitions may include secrets, keys and other cr edentials [5].  
There are two main strategies for mitigating IaC security concerns. The first strategy involves using IaC 
codification and processing tools and frameworks to introduce encodings and codifications for best practices 
and security controls [6] -[9]. The second  strategy is the use of Cloud Security Posture Management (CSPM) 
tools.  
There have been recent studies that integrate artificial intelligence and security to audit IaC configurations. 
These studies have primarily focused on the AWS cloud platform [15] -[19]. 
1.1. Soft Infrastructure Threats  
Software -Defined Infrastructure (SDI) allows for high automation of enterprise computing. With SDI, the 
infrastructure is programmable with code, and changes to the code are automatically deployed with CI/CD 

=== PAGE 2 ===
 
tools. Given the similarities with software development, infrastructure config code (IaC) is treated as source 
code.  
Given the rise in adoption of Cloud Computing, a variety of architectural misconfigurations of IaC have been 
reported and validated [4] [5]. Other studies have reported code repositories have accidentally disclosed 
sensitive information at high rates (e.g.  65% public code repositories reported in [6]).  
Some of the IaC misconfigurations are:  
(i) IaC has defined configuration rules for security groups to control ingress traffic. However, in some cases 
these rules allow administrative traffic over the Internet (e.g. SSH, RDP, Kubernetes API).  
(ii) Sensitive data stored on cloud storage and block storage are unprotected.  
(iii) IaC defines and grants access control to cloud resources. Improper configuration allows access to all 
resources.  
(iv) Sensitive information (e.g. application secrets, access tokens, etc.) are stored in code repos.  
There are other threats like shared or hard -coded admin passwords and use of out -dated or deprecated IaC 
constructs.  
1.2. Failure Modes of Traditional Tools and Open -Loop LLMs  
To illustrate the reason new methods are needed we provide cases for conventional IaC tooling.  
Case 1: Alert Fatigue and Syntactic Myopia: Tools such as Checkov, tfsec, KICS, Trivy, and others, rely 
on syntactic analysis. Therefore, they primarily analyze expressions. As a result, tools report false positives 
at rate between 32.4% to 47.9% and generate a large number of alerts. The tools ulti mately lose developers' 
trust, and alert fatigue sets in.  
Case 2: Diagnostic Gap: Static analysis tools identify security issues in code. However, it is the 
responsibility of the security team to integrate the recommended remediations. This can lead to a 
considerable delay between the discovery and remediation of the issue. On average, it takes 24.6 days to 
resolve a security issue identified by the automated tools [20].  
Case 3: Hallucinations and Dependency Breaking: GPTs and other LLMs can learn to synthesize code. 
However, during code generation, GPTs and LLMs can hallucinate code and create dependencies which 
break during integration. This can result in application failures.  
Case 4: Secret Detection: Secret detection relies on entropy. While tools can help detect secrets, they can 
create a large number of false positives. Hexadecimal codes, UUIDs, and Base64 codes can be identified as 
secrets.  
1.3. Research Contributions  
This research presents AgentShield AI, a closed -loop system built on LangGraph. It uses specific agents to 
resolve IaC security issues. The main contributions of the research are:  
8-Agent Orchestration: This comprises a set of agents to create a closed -loop system.  
Hybrid Tree -sitter Parser: This contains a tree -sitter parser to create a syntax tree. It resolves variables by 
using the scope of the expression.  
Hybrid Dual -Secret Detection: This comprises a combination of a modified Shannon entropy expression 
to find the secret.  
Hybrid Dense -Sparse RAG: This comprises a retrieval system to search the 12,400 CIS and NIST 
framework security rules.  
Calibrated MultiLLM Ensemble: This comprises a system where confidence scores are computed by a set 
of LLMs and a consensus voting system is implemented.  
Zero -Break Code Commits: This comprises a system where generated code is validated to be syntactically 
correct.

2. Related Work and Comparative Landscape  
Security verification tools for IaC can be broken into several categories. They are usually static linters, 
policy -as-code engines, formal verifiers, secret detectors, or neural repair tools.  
2.1. Static Linters and Policy -as-Code Engines  
Some of the earliest generation of tools relied on primitive pattern matching. Checkov parses Terraform 
HCL into a Python abstract syntax tree and applies match rules. tfSec parses Terraform HCL into Go structs 
looking for common anti -patterns. KICS parses  multiple flavors of IaC into JSON then feeds them into Open 
Policy Agent for rules evaluation. Trivy works by scanning both container images and IaC config files for 
CVE matches.  
The major downside to static tools is none of them understand variable value propagation across modules. 
That omission creates failure -to-discover rates between 32 -48% of true positives (false alarms). Policy -as-
code tools like Open Policy Agent (OPA) and Sentinel give engineering teams freedom to author their own 
rules. The drawback to writing custom policy rules is most teams struggle to keep those rulesets up to date 
with cloud provider API changes. Updating rules to support new cloud APIs is difficult t o maintain teams.  
2.2. Formal Verification & SMT Solvers  
Formal verification attempts to mathematically prove a policy will always uphold certain conditions. AWS 
Zelkova converts IAM policies into SMT formulas then tries to prove they can reach a state of 
“Unauthorized”. Cloud -SMR attempts the same process but f or network security configurations.  
Formal verification is sound, but it doesn’t scale. I analyzed a multi -cloud deployment using hundreds of 
microservices. It took 3 hours to process the math. Keep in mind, formal verification can only tell you there 
is a problem. It cannot fix them.  
2.3. Statistical Secret Detection and Entropy Modeling  
Credential scanning tools are almost exclusively regex matchers. Gitleaks and TruffleHog blast codebases 
with regex queries that look for AWS KeyIDs, GitHub tokens, password annotations, etc. There have also 
been studies showing Shannon entropy is effectiv e at detecting secrets that don’t have a well -defined format.  
Entropy is noisy and produces false positives on JWT tokens, UUIDs, commit hashes, and Base64 -encoded 
data. AgentShield AI overcomes this limitation with a hybrid approach. We use sliding entropy in 
conjunction with Tree -sitter scoping queries to dismiss p rintable identifiers.  
2.4. Neural Program Repair and Frontier LLM Fixes  
The rising popularity of LLMs has led to a surge in “auto -apply” vulnerability remediation tools. Toprani 
and Madisetti pioneered the graph -prompt technique using zero -shot Terraform fixes with GPT -3. Their 
sandbox was unable to run compiler checks or Terr aform deployment validations. When deploying GPT -3 
fixed configs into AWS: 28.8% of those configs failed due to hallucinated Terraform attributes and provider 
dependencies.  
Alsaid et al. analyzed numerous pairs of LLM -generated fixes that passed standard linting tools and 
discovered 71.4% had undiscovered bypasses when deployed into real AWS environments. Mengistu et al. 
introduced TerraRepair which showed dependency context drastically reduces hallucinations.  
AgentShield AI expands upon TerraRepair’s premise by adding a dual -LLM consensus voting overlay as 
well as containerized LocalStack/Azurite dry -run validation.

3. Research Methodology  
AgentShield AI coordinates eight specialized agents using an asynchronous, event -driven workflow 
implemented with LangGraph (see Fig. 1). The agents are connected through a directed workflow, where 
each agent handles a particular part of the security analy sis. The system also keeps track of the information 
produced at each stage so that the processing history can be traced when needed. If a particular stage fails, 
automated fallback mechanisms are used to handle the failure and continue the remaining workfl ow where 
possible.

Specialized Multi -Agent Roles (not exactly rigid, but mostly): The autonomous pipeline decomposes IaC 
verification into eight specialized agent roles:  
1) Manager/Router Agent: Accepts the raw multi -cloud templates, determines the type of template (Terraform 
HCL2, CloudFormation, Kubernetes, Helm), and checks that the schema is correct before initiating parallel 
execution in a controlled fashion, similar to a ripple.  
2) Hybrid AST Parser Agent: Splits up the declarative code into standard AST components, resolves dynamic 
references, and handles conditional blocks such as 'count' and 'for_each' before any LLM reasoning is carried 
out. 
3) Secrets Scanner Agent: Works with zero -egress isolation, uses deterministic regex matching together with a 
sliding Shannon entropy evaluation, and basically tries to identify exposed API credentials and private keys 
before they have an opportunity to be transmitted.  
4) RAG Query Agent: Generates combined dense and sparse vector queries against an indexed database that 
includes security benchmarks (such as CIS, NIST SP 800 -53, SOC 2, and PCI -DSS) as well as daily CVE 
feeds in order that the context stays up to date.  
5) Security Analyst Agent: Carries out parallel dual model inference using Claude 3.5 Sonnet and GPT -4o and, 
when appropriate, applies Chain of Thought (CoT) reasoning to produce structured vulnerability hypotheses, 
sometimes adding a bit of narrative as well.  
6) Human Security Audit Queue Agent: Detects cases that have a low confidence level (C_ensemble < 0.85) or 
any cases that conflict, and then queues these results in an interactive web -based triage dashboard for the 
security engineers to review, verify them and possibly reframe them.  
7) Auto Patch Remediation Agent: Creates Unified Diff patches that are both deterministic and syntactically 
correct and is aimed at specific line offsets in the original templates, with the same level of precision.  
8) Code & Sandbox Validator Agent: Carries out a two -stage validation process, beginning with the use of local 
static linters before performing a dry run deployment within containerized LocalStack/Azurite sandboxes.  
3.1. Asynchronous Graph Orchestration and State Contracts  
The eight specialized agents operate within a reactive, event -driven graph coordinated via LangGraph. 
Unlike brittle linear pipelines where a single agent failure aborts the entire execution, AgentShield AI 
employs an immutable typed state schema governed by Pydantic V2 contracts. State transitions are strictly

When an agent experiences an unrecoverable exception (e.g., an unresponsive LLM endpoint), the 
orchestrator triggers automated fallback routing to alternative inference providers or escalates the i tem

Formulations: 1) Dynamic CST Parameter Resolution and Dependency Extraction: Given an IaC template 
T, Tree -sitter generates a Concrete Syntax Tree (G_cst), and parameter, variables and conditional constructs 
are resolved to extract resource dependency graph (G_dep):  
    G_cst = Phi_CST(T_IaC, V, C)   (1) 
Where V and C represent variables and conditional or configuration constructs respectively.  
2) Information -Theoretic Secret Detection: The Shannon entropy of a string literal X is calculated as:  
    H(X) = - Sum_{i=1}^{|Sigma|} P(c_i) * log_2(P(c_i)),  where P(c_i) = Count(c_i, X) / L   (2) 
Where P(c_i) is the relative frequency of character c_i in string X and L is the length of the string. A 
candidate string literal is flagged and identified as a secret by the entropy component when H(X) > TH, 
where the threshold TH is set to 3.8.  
3) Hybrid Dense -Sparse Semantic Relevance: The equation to compute relevance between a query q and 
document d is as follows:  
    S_hybrid(q, d) = alpha * CosineSim(e(q), e(d)) + (1 - alpha) * BM25(q, d)   (3) 
Where alpha = 0.7 and 1 - alpha = 0.3 respectively denote the importance of semantic similarity and sparse 
relevance. BM25 denotes the normalized BM25 function.

4) Calibrated Multi -LLM Ensemble Confidence Metric: The confidence metric for the multi -LLM ensemble 
captures the structural agreement of the LLMs and defines the confidence of a vulnerability finding as:  
    C_ensemble(v) = w_1 * C(M_1, v) + w_2 * C(M_2, v) + gamma * Jaccard(S(M_1), S(M_2))   (4)

4.2. Additional Theoretical Formulations and Algorithmic Metrics  
7) Reciprocal Rank Fusion (RRF) for Hybrid Compliance Retrieval: To combine dense semantic vector 
rankings from Qdrant HNSW with sparse lexical rankings from BM25 without requiring score 
normalization, the RAG Query Agent computes the Reciprocal Rank Fusio n score:  
    RRF_Score(d) = Sum_{m in {Dense, Sparse}} [ 1 / (k_rrf + r_m(d)) ]   (7) 
Where r_m(d) in {1, 2, ..., N} denotes the ordinal rank of compliance passage d under retrieval model m, 
and k_rrf = 60 is the Bayesian rank smoothing constant.  
8) Concrete Syntax Tree Dice Agreement Formulation: The structural node -level agreement between 
candidate diff patches delta_1 (synthesized by Claude 3.5 Sonnet) and delta_2 (synthesized by GPT -4o) is 
evaluated via Dice similarity on CST subtrees:  
    S_dice(delta_1, delta_2) = [ 2 * |Nodes(G_cst(delta_1)) cap Nodes(G_cst(delta_2))| ] / [ 
|Nodes(G_cst(delta_1))| + |Nodes(G_cst(delta_2))| ]   (8) 
A patch is dispatched to the containerized sandbox if and only if S_dice(delta_1, delta_2) >= 0.92, ensuring 
near-perfect structural agreement.  
9) Multi -Cloud Domain -Specific Execution Scoring Function: Candidate patches are evaluated across 
syntactic, planning, and deployment tiers parameterized by provider domain Phi:  
    V_score(delta, Phi) = 0.20 * S_syntax(delta) + 0.30 * S_plan(delta) + 0.50 * S_apply(delta, Phi)  
 (9) 
Where S_apply(delta, Phi) evaluates containerized LocalStack for AWS, Azurite mock storage for Azure, 
GCP Vet for GCP, and isolated K3s clusters for Kubernetes. A patch is accepted if and only if V_score = 
1.0. 
10) Enterprise Financial Expenditure and MTTR Reduction Model: Total monthly enterprise vulnerability 
triage expenditure is modeled as:  
    Cost_total = ( N_FP * T_triage + N_TP * T_action ) * Rate_eng   (10) 
Where Rate_eng = $100/hr, T_triage = 0.30 hr (18 min per false alarm), manual T_action = 2.50 hr, and 
automated AgentShield AI PR review T_action = 0.05 hr (3 min). Developer -in-the-loop MTTR is computed 
as MTTR_org = t_pipeline + t_review + t_deploy, redu cing MTTR from 24.6 days to < 4 hours.  
5. Experimental Setup and Benchmark Methodology  
To rigorously evaluate AgentShield AI across multi -cloud environments, we curated a benchmark corpus of 
2,450 Infrastructure -as-Code templates spanning HashiCorp Terraform (HCL2), AWS CloudFormation 
(JSON/YAML), Kubernetes Manifests, and Helm Charts. This section details dataset composition, ground -
truth auditing procedures, comparative baselines, and test hardware environments.

5.1. Benchmark Corpus Composition  
The evaluation benchmark is constructed from three distinct complementary suites:  
• 1) Production Enterprise Corpus (PEC -1500): 1,500 real -world production templates harvested from top -
starred enterprise repositories across AWS (600 templates), Azure (500 templates), and GCP (400 
templates). Selection criteria mandated >= 50 GitHub stars,  active commits between 2021 and 2025, and >= 
5 declared cloud resources.  
• 2) Synthetic Security Benchmark (SSB -650): 650 synthetic templates containing 3,250 systematically 
injected vulnerabilities mapped to the OWASP Cloud Top 10 and CWE -732, CWE -250, and CWE -798. 
• 3) Toprani -Madisetti Benchmark (TMB -300): 300 complex multi -resource templates from [19] specifically 
designed to evaluate dynamic expression evaluation, ternary operators, and inter -module variable references.  
5.2. Ground -Truth Auditing, Deduplication, and Baselines  
Ground truth was established through triple -blind manual verification conducted by three certified senior 
cloud security architects (each possessing >= 5 years of enterprise DevSecOps experience). Discrepancies 
were resolved through consensus review agains t CIS Cloud Benchmarks (AWS v3.0, Azure v2.1, GCP v2.0) 
and NIST SP 800 -53 Rev. 5 controls, achieving an inter -annotator concordance of Cohen's Kappa = 0.91. 
Near -duplicate templates were eliminated via a two -stage deduplication pipeline (CST MinHash with 
Jaccard threshold 0.85 and SHA -256 digest matching), purging 418 duplicate templates.  
AgentShield AI was evaluated against four leading static linters (Checkov v3.2 [6], tfsec v1.28 [7], KICS 
v2.1 [8], Trivy v0.51 [9]), two zero -shot frontier LLMs (Zero -Shot GPT -4o, Zero -Shot Claude 3.5 Sonnet), 
and the base IEEE framework by Toprani & Madi setti (2025) [19]. All benchmarks executed on an AMD 
EPYC 7763 workstation (64 physical cores, 2.45 GHz), 256 GB DDR4 RAM, dual NVIDIA RTX 4090 
GPUs (24 GB VRAM each), running Ubuntu 22.04 LTS, Docker Engine 26.1, LocalStack v3.4, and Azurite 
v3.30. All me trics report the mean across 5 independent randomized runs, with statistical significance 
established using two -tailed Wilcoxon signed -rank tests (p < 0.001).

9. Threats to Validity, Operational Constraints and Recommendations  
Although the results obtained from the different studies have confirmed the strength and potential of 
AgentShield AI, there are a number of aspects related to the design and implementation of the studies that 
deserve attention.  

=== PAGE 18 ===
 
1. Internal and External Validity: Internal validity was ensured by means of triple -blind, manual ground truth 
auditing (Cohen’s Kappa 0.91) and MinHash to eliminate datasets fork. For assessing external validity, we 
analyzed 2450 multi -cloud templates. Th ese templates enable users to configure cloud infrastructure using 
tools such as Terraform and AWS CloudFormation as well as Kubernetes. Other tools included in the 
analysis are Helm and custom Internal DSLs. Custom Internal DSLs are often defined in JSON.  Tree-Sitter 
is a software package that can be extended to provide syntax analysis for JSON; therefore, it can be used to 
extend the DSL definition.  
2. Local Container Sandbox vs. Hyperscaler Equivalence: LocalStack and Azurite provide high fidelity 
emulations of some cloud provider control planes. However, they do not provide any emulation of physical 
boundaries of hyperscaler data centers, live cross -account identity federation, or enterprise conditional 
access policies.  
3. Enterprise Phased Adoption: We recommend an aggressive phased adoption to AgentShield AI. During 
the first phase of 2 weeks, audit mode was activated to generate Security Incident Response (SIR) reports in 
the SARIF format. During the second phase, reme diation was restricted to enable storage element encryption 
and audit logging. During the last phase, remediation was fully automated, and, based on the confidence 
level of AgentShield AI, remediation actions were executed. Human review was triggered by Ag entShield 
AI for recommendations it made with a confidence level of less than 0.85.  
10. Conclusions  
AgentShield AI brings together multiple agents to secure multi -cloud infrastructure -as-code solutions. The 
framework covers three main tasks: checking syntax, detecting exposed credentials, and testing fixes in a 
sandbox before they are applied.  
The framework was developed to address some of the common problems with static checkers and open -loop 
LLMs. Static checkers can generate a large number of false positives, while open -loop LLMs may produce 
fixes that cannot be executed because of token hall ucinations. They can also introduce broken dependencies 
that cause deployment failures.  
The system brings together eight specialized agents through LangGraph. It uses Tree -sitter to resolve 
dynamic parameters, a dual -engine approach to detect leaked secrets, and a hybrid search system covering 
12,400 CIS and NIST rules. It also uses Claude 3. 5 Sonnet and GPT -4o for consensus -based voting. Proposed 
fixes are then tested through a two -tier validation harness using containerized LocalStack and Azurite 
sandboxes.  
The framework was evaluated on 2,450 multi -cloud templates covering Terraform, CloudFormation, 
Kubernetes, and Helm. It achieved 99.1% precision and 98.4% recall, with a false -positive rate below 0.05%. 
The first -pass sandbox patch acceptance rate was 97.8 %, increasing to 99.4% after automated multi -pass 
retries. Each template took an average of 1.84 seconds to process. These results were higher than those of 
the static analyzers and open -loop LLM baselines used in the evaluation.  
Some limitations remain. Although local sandboxes can simulate cloud provider control planes, they cannot 
fully reproduce physical data centers. Multi -cloud identity federation also introduces complex permission 
boundaries, making regular updates to securi ty rules necessary.  
Future work will focus on two areas. One is developing self -healing loops that use provider telemetry APIs 
to detect and continuously reconcile changes in live cloud infrastructure. The other is reducing multi -LLM 
reasoning into edge -optimized Small Langua ge Models (SLMs) that can perform security checks locally 
within developer IDEs, with sub -second execution and privacy preservation.
